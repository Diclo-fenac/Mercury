# Mercury Project: Inside Out Overview

Welcome to **Mercury**, an advanced, production-ready AI Assistant framework. This document provides a deep dive into the project's architecture, its current status, and the roadmap for full generalization and production deployment.

---

## 🏗️ Architecture: The 6-Layer Clean Design

Mercury is built on a robust, modular **Clean Architecture** to ensure scalability, testability, and maintainability.

### 1. **API Layer (FastAPI)**
- **Role**: Entry point for all external requests.
- **Endpoints**: `chat`, `search`, `products`, `users`, `conversations`, `images`, `cache`, and `health`.
- **Location**: `app/api/v1/endpoints/`

### 2. **Orchestration Layer**
- **Role**: Coordinates complex multi-service workflows.
- **Key Orchestrators**:
    - `SearchOrchestrator`: Combines hybrid search results with personalization.
    - `ChatOrchestrator`: Manages the flow between the LLM, memory, and tools.
- **Location**: `app/orchestrators/`

### 3. **Intelligence Layer (Google Gemini)**
- **Role**: The "brain" of the assistant.
- **Components**:
    - `IntelligenceEngine`: Integrates with Google Gemini for advanced reasoning.
    - `CapabilityChain`: Handles complex, multi-step tasks.
    - `Tools`: Specialized tools for product lookup, user personalization, and image processing.
- **Location**: `app/intelligence/`

### 4. **Add-ons Layer (Core Features)**
- **Role**: Domain-specific enhancements.
- **Key Add-ons**:
    - `HybridSearch`: Merges semantic search (Qdrant) with keyword search (Typesense/Firestore) using Reciprocal Rank Fusion (RRF).
    - `PersonalizationScorer`: Tailors results based on user history and preferences.
- **Location**: `app/addons/`

### 5. **Domain Services Layer**
- **Role**: Encapsulates core business logic.
- **Services**: `ProductService`, `UserService`, `ConversationService`, `RecommendationEngine`.
- **Location**: `app/domain/`

### 6. **Infrastructure Layer (Abstraction)**
- **Role**: Clean interfaces for external systems.
- **Integrations**: Redis (Cache), Firestore (DB), Qdrant (Vector DB), GCS (Storage).
- **Location**: `app/infrastructure/`

## 🚀 Roadmap: Generalization & Production-Readiness

### 1. **Generalization (Domain Agnostic)**
- **Schema-Agnostic Search**: Currently, the `HybridSearch` and `ProductService` are optimized for retail (brands, sizes, colors). Generalizing this requires making the search schema configurable via external JSON definitions.
- **Modular Tools**: Abstract the `intelligence/tools/` to allow easy plug-and-play for different domains (e.g., Finance, Healthcare, Support).

### 2. **Production-Readiness**
- **Enhanced Testing**: Move from simple scripts to a full `pytest` suite with high coverage for orchestrators and domain logic.
- **Resilience Patterns**: Implement circuit breakers (e.g., `resilience4j` style) for external search engines and LLM APIs.
- **Observability**: Integrate OpenTelemetry for distributed tracing and Prometheus for performance metrics.
- **Secure Secret Management**: Transition from `.env` files to cloud-native solutions like GCP Secret Manager.
- **CI/CD Pipeline**: Automate builds, testing, and deployment to staging/production environments.

## ✅ Project Validity Assessment

**Is Mercury a valid project?**
Absolutely. Mercury is more than just a simple chatbot; it is a **sophisticated RAG (Retrieval-Augmented Generation) framework**.

**Why it stands out:**
1. **Clean Architecture**: It avoids the "spaghetti code" trap common in AI projects, making it enterprise-ready.
2. **Hybrid Search**: Most AI assistants rely solely on vector search, which often lacks precision. Mercury’s hybrid approach is the industry gold standard.
3. **Orchestration**: The separation of orchestration from domain logic allows it to handle complex, multi-step user intents that simple LLM wrappers cannot.

**Verdict**: Mercury is a rock-solid foundation for any high-performance, personalized AI assistant.
